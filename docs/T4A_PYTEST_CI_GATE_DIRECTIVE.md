## 0. なぜこれを作るのか — 推測ではなく、ロードマップ自身の要求

`docs/ROADMAP_IOS_TAURI_V2.md` §14 のリスク表は、最高 severity の項目についてこう定めている。

| Risk | 影響 | 早期検証 | 停止/分岐 |
|---|---|---|---|
| app-owned socket 混入 drift | **絶対孤立の毀損** | **symbol/packet/permission 三面 scan の CI 恒久化** | **1 件でも検出したら release 停止** |

同表にはもう一行ある。

> **desktop regression** → 停止: **「desktop suite 不合格なら merge 禁止」**

**この 2 つの停止条件を支える検査は、既に書かれている。**

```
tests/test_e0a_egress_lockdown.py                  AST レベルの物理封鎖検査
tests/test_fsa_2026_07_13_01_offline_boundary.py
tests/test_manifest_persistence_isolation.py
→ 22 passed in 0.25s（実測）
```

**しかし CI では一度も走っていない。** 現存ワークフローは 4 本（`blackbox-profile-write-gate` / `flavor-gate` / `build-macos` / `build-windows`）で、**どれも pytest を実行しない。** 805 件のテストは開発機の上にしか存在しない。

**これは本プロジェクトが繰り返し潰してきた欠陥の型そのものである —— 書かれているが、走っていない。** 今回はそれが最高 severity のリスクの上で起きている。

**T4-A の目的は 1 つ**: この 2 つの停止条件を、**初めて実効化する**こと。

| `pytest tests/ --collect-only -q` | **805 tests collected** | 同上 |

### 2.1 ⚠ 収集数と結果数が 1 件ずれている

**`--collect-only` は 805、実行結果は 804 + 2 = 806。** モジュールレベル skip の計上差に起因すると見られる。

> **したがって件数は「厳密一致」で表明してはならない。床（floor）で表明せよ。** 厳密一致は `textual` を導入した瞬間に壊れ、正しい変更を赤にする。理由 §4.2。

## 3. skip の 2 件は種類が違う。これが本ゲートの核心である

```
SKIPPED tests/test_ui_smoke.py:21
        could not import 'textual': No module named 'textual'

SKIPPED tests/test_fsa_2026_07_13_02_stdio_llm_boundary.py:109
        Windows AppContainer pipe contract
```

| # | skip | 種別 | 正しい扱い |
|---|---|---|---|
| 1 | `textual` 不在 | **環境の欠落** | **依存を入れて測れ。** 書かれたテストが走らない状態を CI で固定するな |
| 2 | Windows AppContainer | **プラットフォーム境界** | macOS/Linux ランナーでは**原理的に測れない**。skip は正しい。ただし**名指しで可視化**せよ |

**この区別が「沈黙の一意性」の実体である。** 両方とも `SKIPPED` の一語で緑の中に埋もれる。**埋もれさせるな。**

## 4. 厳守要件

### 4.1 依存は明示的に入れる

`pytest` / `numpy` / **`textual`** を install すること。**`textual` を省いてはならない** —— 省けば §3 の skip #1 が CI で恒久化し、「書かれているが走っていない」テストを我々自身が新造することになる。

### 4.2 【自己試験】収集数の床を表明せよ

**本ゲートの最大の失敗様式は「0 件収集して緑で終わる」である。** ディレクトリ指定ミス、import エラーの握り潰し、パス解決の失敗 —— いずれも「失敗が無い」ので緑になる。

**収集数が床を下回ったらジョブを落とせ。**

```
collected >= 800
```

> **根拠**: 起草者は本セッションで `strings`（UTF-8 を拾わない）と `system_profiler`（0 行を返す）の 2 つの死んだ検出器に騙されかけた。**検証していない検出器の沈黙を証拠にしてはならない。** 本リポジトリには既に同型の前例がある —— `flavor-gate` の `--lib flavor floor (≥ 26, 0 ignored)`。**その慣習に従え。**

**厳密一致（`== 804`）で書くな。** §2.1 のとおり収集数と結果数は既に 1 ずれており、`textual` 導入で更に動く。**床は「壊れていないこと」を測る。厳密一致は「変化しないこと」を測ってしまう。**

### 4.3 【沈黙の一意性】skip を名指しで可視化し、未知の skip は落とせ

- **全 skip をログに理由付きで列挙**すること（`-rs` 等）
- **許容する skip は §3 の #2（Windows AppContainer）のみ。** それ以外の skip が 1 件でもあれば**ジョブを落とせ**
- 許容 skip についても、**「測っていない」と明記した行をログに出す**こと

> **理由**: `leaked=0` を我々は 2 度、証拠として報告した。**どちらも空虚だった** —— 撃墜対象が飛来していないのだから、何も見つからないのは当然で、能力について何も述べていなかった。**「測って 0 だった」と「そもそも測っていない」は、同じ 0 に見えて意味が正反対である。** ログがその区別を語らないゲートは、緑であることの意味を語れない。

### 4.4 絶対孤立の 3 ファイルは独立ステップにし、独自の床を持たせよ

```
tests/test_e0a_egress_lockdown.py
tests/test_fsa_2026_07_13_01_offline_boundary.py
tests/test_manifest_persistence_isolation.py
→ 床: collected >= 22 / failures == 0
```

**全体 805 件の中に埋めるな。** §14 が release 停止条件として名指ししている検査である。**CI の画面上で「絶対孤立」という名前で見えること**、および**誰かがファイルを消したら床が落ちること**を要件とする。

### 4.5 ランナーは `macos-14` とせよ

**`ubuntu-latest` の方が安価で速いが、採用しない。** §2 の 804/2 は macOS で測った値であり、**Linux で同じになるという証拠が無い。**

> **根拠（本プロジェクトの実績）**: Tier 2（シミュレータ）の GREEN は Tier 3（実機）を保証しなかった。ピッカーの `fileAccessMode` 既定が環境で分岐し、シミュレータでは成功する経路しか踏んでいなかった。**「別環境でも同じはず」は、この隊では証拠として通らない。**
>
> Linux 化は **T4-A 完了後に、実測を添えて**別途提案せよ。本指示書の範囲では採用しない。

### 4.6 GGUF スタブは不要 —— ただし確かめてから断言せよ

pytest は純 Python であり `build.rs` を通らないため、`flavor-gate` / `blackbox-profile-write-gate` に入れた GGUF プレースホルダは**不要と見ている。**

**しかしこれは起草者の推定である。** 実装時に**スタブ無しで実際に緑になることを確認**し、確認した事実として報告せよ。**必要だと判明したら、その事実を報告した上で入れよ。** 推定を根拠に省略するな。

### 4.7 トリガ

既存 2 ゲートに合わせよ。

```yaml
on:
  pull_request:
  push:
    branches: [main, master]
  workflow_dispatch:
```

> **注意**: `workflow_dispatch` はデフォルトブランチに登録されるまで起動しない（本セッションで実測）。**PR #1 上で `pull_request` により走ることが、本ゲートの唯一の起動経路である。**

## 5. 受入条件（起草者はこれで監査する）

| # | 条件 | 判定方法 |
|---|---|---|
| A-1 | PR #1 上でジョブが**実際に起動する** | `gh run list` に出る |
| A-2 | **失敗 0** | pytest exit 0 |
| A-3 | **収集数 ≥ 800** をジョブが自ら検査し、下回れば落ちる | ログに実数が出る |
| A-4 | **絶対孤立ステップが独立**し、床 ≥ 22 を自ら検査する | ログに実数が出る |
| A-5 | **全 skip が理由付きで列挙**される | ログに出る |
| A-6 | **未知の skip でジョブが落ちる** | 実装を読んで検証 |
| A-7 | **`textual` が install され、skip #1 が消えている** | skip 一覧に textual が無い |
| A-8 | 許容 skip（Windows）が**「測っていない」と明示**される | ログの文言 |
| A-9 | 既存 4 ワークフローが**無改変** | `git diff` |
| A-10 | GGUF スタブの要否が**実測に基づいて**報告される | 報告文 |

### 5.1 変異ドリル（A-3 / A-6 の実証）

**「床が実際に落とすこと」を、落ちるところを見せて証明せよ。** 4 点セットで報告すること。

1. 床を一時的に `>= 100000` にする（または収集対象を空にする）→ **ジョブが赤になる生ログ**
2. 未知の skip を 1 件人為的に作る → **ジョブが赤になる生ログ**
3. 復元
4. **緑に戻る生ログ**

> **根拠**: 本セッションで、CI のスタブ生成を「入れた」が `working-directory` を確認せず、**同じエラーで落ち続けた。** 入れたことと効いていることは別である。**ゲートがあることと、ゲートが落とせることも別である。**

## 6. 禁止事項

- 既存 4 ワークフローの改変
- `continue-on-error` / `|| true` による失敗の握り潰し
- テスト件数の**厳密一致**表明（§4.2）
- 失敗するテストを skip / xfail へ退避させること（**赤は事実であり、隠す対象ではない**）
- `ubuntu-latest` への変更（§4.5。提案は歓迎するが本指示書の範囲外）
- **測っていない事柄を「問題なし」と報告すること**

---

## 7. 報告様式

**コマンドと生出力の対で報告せよ。数値だけの要約は無効。**

1. 追加したワークフローの全文
2. PR #1 上での実行結果（run ID・結論・所要時間）
3. **収集数・skip 一覧の生ログ**
4. §5.1 変異ドリルの 4 点セット
5. GGUF スタブの要否（実測に基づく事実として）
6. **実施しなかったこと・確かめなかったことがあれば、その旨を明記** —— 「たぶん大丈夫」は報告ではない

---

## 8. 本ゲートが守るもの

このゲートが緑であることは、以下を意味する。

- **絶対孤立の AST 物理封鎖検査が、実際に走った**（§14 最高 severity・release 停止条件）
- **desktop suite が、実際に走った**（§14・merge 停止条件）
- **収集が 0 件ではなかった**（検出器が生きている）
- **測れなかったものが、名指しで記録された**（沈黙の一意性）

**緑が「何も問題が無い」ではなく「何を測って問題が無かったか」を語るゲートにせよ。** それが本プロジェクトの唯一の作法である。
