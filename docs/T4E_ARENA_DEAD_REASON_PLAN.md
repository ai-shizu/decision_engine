## 0. まず、言葉を分ける必要がある

主目標は「再現と根治」だが、**この二つは同じ対象を指していない可能性がある。**

`arena.dead_reason` は**バグではなく計器**である。`f14cc10` で追加された OSLog 数値出力で、iOS Release がアリーナの死因を飲み込む問題（G-0R）に対する回答だった。

```rust
// blackbox_arena/handle.rs:999
#[cfg(target_os = "ios")]
fn log_arena_terminal_ios(state: SessionState, turns: u32) {
    log_model_u64("arena.sealed", sealed);
    log_model_u64("arena.dead_reason", reason);
    log_model_u64("arena.turns_completed", u64::from(turns));
}
```

**「未再現」が意味しているのは「この計器が非ゼロを一度も出していない」である。**

> **本プロジェクトが最も警戒してきた状態そのものだ。** 赤を出したことのない計器は、赤を出せない計器と区別が付かない。
>
> `arena.dead_reason` は**今日まで一度も赤くなっていない。** それが「壊れていない」のか「発火し得ない」のかを、**まだ誰も測っていない。**

したがって着工順序は「バグを探す」ではない。**「計器が発火し得るかを先に確定させる」**である。

## 1. 起草者が既に実測した事実

### 1.1 `Dead` は本番経路から到達可能である

`director.rs` の `self.die(FailureReason::…)` 呼び出しを数えた。

| `FailureReason` | コード | 本番 `die()` 呼び出し |
|---|---|---|
| `AccountingBreach` | 1 | **1 箇所**（`director.rs:658`） |
| `SnapshotDigestMismatch` | 2 | **1 箇所**（`director.rs:669`） |
| `ReplayDivergence` | 3 | **0 箇所** |
| `InternalInvariantBroken` | 4 | **2 箇所**（`director.rs:583, 661`, 他 686） |

### 1.2 **コード 3 は本番で emit され得ない**

`FailureReason::ReplayDivergence` の出現箇所は全て、コード表・そのテスト・enum 宣言・fsm のテストに限られる。**`die()` に渡している本番コードが存在しない。**

一方 `bridge.rs` には**別の enum** `BridgeError::ReplayDivergence` があり、`bridge.rs:191` で fail-close している。

```rust
// bridge.rs:17  「2. Fail-closes on any digest mismatch (BridgeError::ReplayDivergence)」
```

**つまり replay 乖離は検出されているが、セッション FSM の死には接続されていない。**

これが欠陥（検出したのに殺していない）なのか設計（bridge が別に処理し FSM 側の variant は遺物）なのかは、**まだ判定していない。推測で埋めない。**

## 2. タスク分解

### T4-E-1 — 到達可能性の棚卸し（**最初にこれをやる**）

4 コードそれぞれについて、**本番入力から到達する経路が存在するか**を実測し、表で示す。

- 経路が在るなら、**どの入力が引き金か**
- 経路が無いなら、**その事実を記録する**（コード 3 が該当する見込み）

**「たぶん到達する」を書かせない。** 呼び出し元を辿った根拠を添える。

### T4-E-2 — 陽性対照：**計器が非ゼロを出せることの証明**

`arena_terminal_codes` は `const fn` で、doc コメント自身が「host tests で mapping を assert するため `cfg(target_os)` を付けていない」と述べている。**mapping のテストは既にある**（`handle.rs:1130-1133`）。

だが**証明されていないのは mapping ではなく経路**である。

1. 実セッションを `Dead` へ落とし、`arena_terminal_codes` が `(1, N)` を返すことを host テストで示す
2. **iOS 経路**（`log_arena_terminal_ios`）は `cfg(target_os = "ios")` 下にあり、**どの CI でも走らない** — [[host-test-coverage-gaps]] が記録した「iOS-only テストはどこでも走らない」型に該当する。**ここを純ロジックとして切り出せないか検討する**

> §1 の doc コメントは `sanitize_one_liner` を引き合いに出している——**「iOS-only テストが一度も走らず、数か月にわたり偽を assert していた」**。同じ構造が `log_arena_terminal_ios` に残っている。

### T4-E-3 — 各 `die()` サイトの発火条件を特定

`director.rs:583 / 658 / 661 / 669 / 686` それぞれについて、**どの状態でどの入力が来ると発火するか**を述べる。テストから駆動できるかを判定する。

### T4-E-4 — 再現

到達可能と判定した各コードについて、**実際にセッションを死なせる**再現手順を作る。

### T4-E-5 — 根治（**条件付き**）

**ここで初めて「バグかどうか」を問う。**

| 観測 | 意味 | 対処 |
|---|---|---|
| 正当な入力で `Dead` に落ちる | **欠陥。**不変条件が実際に破れている | 根治する |
| 破損した状態からのみ `Dead` | **正常。**FSM が正しく fail-close している | 直すものは無い。記録して終える |
| 経路が存在しない（コード 3） | **計器の死角**か設計上の遺物 | §1.2 の判定次第 |

**`Dead` は「正しい振る舞い」でもあり得る。** FSM が破損検出後に進行を拒否している状態であって、それ自体は欠陥ではない。**「根治」を前提に着工すると、壊れていないものを直しにかかる**——T4-D で S-3 について起草者が実際にやった誤りである。

## 4. 本フェーズの成否を分けるもの

T4-D は「接続の証明が、接続先の実行不能によって不可能になっている」を閉じた。

**T4-E が問うのは、その一段手前である——「この計器は、そもそも赤くなれるのか」。**

`arena.dead_reason` は監視項目として引き継がれ、「未再現」と報告され続けてきた。**だが未再現には二つの意味がある。**

- **事象が起きていない** —— 監視を続ける価値がある
- **計器が発火し得ない** —— 監視は何も守っていない

**この二つを区別しないまま監視を継続することは、沈黙を安全と読み替えることである（鉄則 2 の違反）。** T4-E-1 と T4-E-2 が終わるまで、`arena.dead_reason` の緑には意味が無い。
