## 0. これを書いている理由 — **既に 1 件、見つかっている**

起草者が本指示書のために現行アーカイブを実測したところ、**§15.2 絶対孤立 DoD の違反が既に出荷経路に載っていた。**

```
Coraxis.app/Info.plist:
  NSAppTransportSecurity
      NSAllowsArbitraryLoadsInWebContent = true
      NSAllowsLocalNetworking            = true
      NSExceptionDomains: 10.0.0.0/8 …
  NSLocalNetworkUsageDescription = "開発時のみ、同じ Wi-Fi 上の Mac（Vite :1420）へ…"
```

ロードマップ §15.2 は **「network 系 plist key 0」** を、§14 は **「1 件でも検出したら release 停止」** を定めている。

**出所**: `apps/desktop/src-tauri/tauri.ios.conf.json:34` が `Info.ios.plist` を**無条件**で指しており、dev/release の分岐が無い。**実機 HMR のために入れたキーが、全ビルドに載り続けている。**

### 0.1 なぜ今まで気づかなかったか —— **走っていた検査が、構造的に見られなかった**

起草者は本セッション中、実機インストール前に毎回この検査を手で回した。**8 回走り、8 回とも 0 を返した。**

```bash
strings "$APP/Coraxis" | grep -cE '://(10|172|192)\.[0-9]+\.[0-9]+\.[0-9]+:[0-9]+'   # → 0
```

**この正規表現は `://` と `:port` を要求する。** plist にあるのは `10.0.0.0/8` —— **`://` も `:port` も無い CIDR 表記**である。しかも走査対象が**バイナリのみ**で、`Info.plist` を一度も見ていない。

> **本フェーズが繰り返し見つけた欠陥に、第四の型が加わる。**
>
> 「書かれているが、走っていない」／「走っているが、届いていない」／「走っていて、届いていて、常に同じものを届けている」——そして今回は **「走っていて、緑を返していて、対象を見ていない」。**
>
> **緑は「問題が無い」ではない。「その検出器が見る範囲に問題が無い」でしかない。** 範囲を書き残さない検査は、緑の意味を誰にも説明できない。

**T4-B の目的は、手作業の自動化ではない。手作業では覆えていなかった範囲を、明示された範囲として固定することである。**

## 4. 厳守要件

### 4.1 【最重要】すべての検査に**陽性対照**を持たせよ

**各検査は、自分が「検出できること」を毎回自分で証明してから、本番対象を測れ。**

```
① 既知の違反サンプルを検査器に食わせ、検出することを確認する（陽性対照）
② 対照が検出できなかったら、そこでスクリプトを落とす
③ そのうえで本番対象を測る
```

> **根拠**: 本セッションで起草者は 3 つの死んだ検出器に騙されかけた。
> - `strings` は **UTF-8 を拾わない** —— 日本語文字列を 0 件と報告した（`grep -a` で 1 件）
> - `system_profiler SPUSBDataType` は **0 行**を返した（環境で無効）
> - dev-URL 正規表現は **CIDR 表記を見られない**（§0.1・本ゲートが存在する理由そのもの）
>
> **検証していない検出器の沈黙を、証拠にしてはならない。** 対照が無い検査は、緑を報告する資格が無い。

### 4.2 文字列走査は `strings` に頼るな

`strings` は既定で **ASCII 印字可能列のみ**を拾う。**UTF-8 の日本語・CIDR・非 ASCII を含む対象には使えない。** バイナリ横断検索は **`grep -a`** を用い、§4.1 の陽性対照で証明せよ。

### 4.3 走査対象を**明示的に列挙**し、範囲をログに書け

**バイナリだけを見て緑を出すな。** 最低限、以下を対象として明示すること。

- `Coraxis.app/Coraxis`（Mach-O 本体）
- `Coraxis.app/Info.plist`
- `Coraxis.app/embedded.mobileprovision`
- `Coraxis.app/assets/models/pocket-brain.gguf`

**ログの冒頭に「何を走査したか」を出力せよ。** 緑の意味は、走査範囲とセットでなければ確定しない。

### 4.4 「測って 0」と「測っていない」を書き分けよ

対象ファイルが存在しない場合、**0 件と報告するな。** `ABSENT` として区別し、それが許容される状況か否かを明示せよ（既存 `gguf_three_point_sha_gate.sh` の `ABSENT` 扱いが先例である）。

### 4.5 dev 署名と release 署名を区別せよ

`get-task-allow = true` は開発署名では正常である。**これを一律違反とすると、開発ビルドで常時赤になり、ゲートが無視されるようになる。**

- 検査は**署名種別を判定し、ログに明記**する
- **Release 署名でのみ** `get-task-allow` を違反として扱う
- 判定できない場合は **`UNKNOWN` として落とせ**（推測で通すな）

### 4.6 終了コードを項目別にせよ

どの検査で落ちたかが exit code から分かること。`gguf_three_point_sha_gate.sh` の `12/13/14` が先例である。

### 4.7 既存スクリプト・ワークフローを改変するな

`scripts/gguf_three_point_sha_gate.sh` と `.github/workflows/` の 5 本はすべて無改変。

## 5. 変異ドリル（必須・各検査ごと）

**「ゲートがあること」と「ゲートが落とせること」は別である。** S-1〜S-7 の**各項目について**、落ちるところを見せよ。

各項目につき 4 点セット:

1. 違反を人為的に作る（例: 一時コピーの Info.plist に network キーを足す / バイナリに dev URL 文字列を仕込む）
2. **スクリプトが赤になる生出力**（項目別 exit code を含む）
3. 復元
4. **緑（または現状どおりの判定）に戻る生出力**

> **S-4 は現状で RED であるため、逆向きのドリルを行え** —— 違反キーを取り除いたコピーを作り、**緑になること**を示せ。**赤いままの検査は、赤を出す能力しか証明していない。**

## 6. 本指示書が**やらないこと**（意図的な範囲外）

- **CI 化はしない。** iOS アーカイブの生成には署名と約 7 分のビルドが要り、CI で恒久化するには別途の設計判断（署名鍵の扱い、実行頻度）が必要である。§14 が求める「CI 恒久化」の**第一段階**として、まずローカル実行可能な検査器を確立する
- **`Info.ios.plist` の修正はしない。** dev/release 分岐の導入は HMR 開発ループに影響する製品判断であり、**指揮官の裁定事項**である。**本ゲートは違反を検出して落ちるところまでを担う**
- **違反の allowlist を作るな。** 「既知の違反だから通す」機構は、このプロジェクトが最も嫌う形である。**赤は赤のまま報告せよ**

## 8. 報告様式

**コマンドと生出力の対で。数値だけの要約は無効。**

1. `scripts/ios_archive_scan.sh` の全文
2. 現行アーカイブに対する**実行結果の生出力**（S-4 の RED を含む）
3. **各項目の変異ドリル 4 点セット**
4. 陽性対照が実際に機能していることの生出力
5. **実施しなかったこと・確かめなかったことの明記**

## 9. このゲートが守るもの

§15.2 は「絶対孤立」を DoD に据えている。その検査は今日まで**人間の手と記憶に依存**しており、**その手作業は範囲が不完全だった** —— 8 回連続で緑を返しながら、実在する違反を一度も見ていなかった。

**このゲートが緑を報告するとき、それは「何を走査して緑だったか」を同時に述べなければならない。** 範囲を語れない緑は、次に誰かが同じ穴に落ちる。

**そして本ゲートは、最初の実行で赤くなる。** それが、このゲートが必要だったことの証明である。
